# RFC 2047 encoded words and header text (ROB-030)

Issues #25 and #26. Implementation: `rfc2047.go`; call sites in `charset.go`,
`header.go` and `progress.go`. Tests: `rfc2047_test.go`,
`rfc2047_example_test.go`, `charset/rfc2047_test.go`.

The rule throughout: decode what can be decoded, leave the rest exactly as it
was written, keep the raw value in the `Header`, and say what was repaired.
Nothing here rejects a value.

## API

| API | Result |
|---|---|
| `DecodeHeaderText(s) (string, []Diagnostic)` | Best decoding of a field value plus a report. Never fails. |
| `DecodeHeaderTextWithOptions(s, *HeaderTextOptions)` | Same, with `FallbackCharset`. |
| `(*Header).TextDiagnostics(k)` / `TextWithOptions(k, opts)` | Same for the field `k`; every diagnostic has `Field == k`. |
| `HeaderFields.TextDiagnostics()` | Same for the current field of an iteration. The interface is sealed, so the new method breaks no implementer. |
| `(*Header).Text(k)`, `HeaderFields.Text()`, `mail.Header.Subject()` | Unchanged signatures, now the same best decoding. The error is the first charset failure of the value (see below) and comes **with** the usable string. |
| `HeaderTextOptions.FallbackCharset` | Charset of text that carries no usable label. |
| `CodeRFC2047WordLimit` (`rfc2047.word_limit`) | New code, appended to the charset block. |

A diagnostic's `Location` is a byte range **within the field value** (what
`Header.Get` returns), not within the message. `Field` is empty from
`DecodeHeaderText` and set by the `Header` methods. At most 64 diagnostics are
reported per value; the 64th is a `limit.diagnostic_count`. Decoding is not
affected by that budget.

`Header.Text` returns a non-nil error only when a word's charset could not be
converted: `IsUnknownCharset(err)` for a charset the `CharsetReader` hook does
not know (or no hook), `io.ErrNoProgress` for a hook reader that stalled, or
whatever error the hook's reader returned. A value holding one such word comes
back unchanged with the error, exactly as before; a value holding more comes
back with everything else decoded. No other defect is an error.

Parameter values of `Content-Type` and `Content-Disposition`
(`metadataDecoder.decode`, so `Header.ContentType`, `ContentDisposition`,
`Entity.Effective…`, and `mail` attachment filenames) use the same word decoder
through `decodeParameterValue`. Text outside encoded words is passed through
byte for byte there, because a `boundary` is compared with body bytes.

## Status per item

### ROB-030-001 — conformant B/Q words, adjacent-word white space: done

- RFC 2047 section 8 examples pass, with the charset plugin and without it
  (`utf-8`, `us-ascii`, `iso-8859-1` need no hook).
- White space between two decoded words is dropped; white space between a word
  and plain text, or next to a word left verbatim, is kept.
- Charset labels are matched case-insensitively; `b`/`q` in either case; hex
  digits in either case.
- Round trip with the encoder: `SetText` then `Text` returns the string for
  ASCII, Latin, Hangul and astral text long enough to be split into many words.

### ROB-030-002 — embedded and otherwise misplaced words: done

Decoded, and reported with `SeverityRecovered`:

| Input | Code |
|---|---|
| word glued to text, or two words with nothing between (`abc=?…?=def`) | `rfc2047.embedded_word` |
| word inside a quoted string (only when the value's quotes balance) | `rfc2047.illegal_location` |
| white space or a fold inside base64 text | `rfc2047.invalid_base64` |
| line break inside Q text (dropped; a space is kept) | `rfc2047.invalid_q` |
| no closing `?=`: decoded up to the next white space, `=?` or end | `rfc2047.invalid_word` |
| empty charset (`=??Q?…?=`) | `charset.empty` |

Not reported because they are not defects: a word longer than 75 bytes, an
RFC 2231 language suffix (`=?utf-8*en?…`), a quoted charset label, literal
space inside Q text.

Adjacent words of the same charset (after normalisation; `B` and `Q` may mix)
are joined as **bytes** before the charset is converted. A multi-byte character
or an ISO-2022 escape sequence split across words is therefore read whole. The
hook is called once per such run, not once per word.

There is no strict mode. A caller that wants strictness treats a non-empty
diagnostic list as a rejection.

### ROB-030-003 — malformed and unknown words keep their neighbours: done

| Input | Result | Code, severity |
|---|---|---|
| unknown charset | word(s) verbatim | `rfc2047.unknown_charset`, unsupported, `Cause` set |
| unknown encoding letter | word verbatim | `rfc2047.unknown_encoding`, unsupported |
| base64 without padding, with surplus or misplaced padding, URL-safe alphabet, foreign bytes | decoded | `rfc2047.invalid_base64`, recovered |
| base64 that yields no byte, or more foreign bytes than base64 ones | word verbatim | `rfc2047.invalid_base64`, invalid_metadata |
| Q with a malformed `=XX`, a bare `?`, raw 8-bit or control bytes | decoded, the offending bytes kept as text | `rfc2047.invalid_q`, recovered |
| hook reader fails, stalls or over-expands | word(s) verbatim | `rfc2047.invalid_word`, invalid_metadata, `Cause` set |
| `unknown-8bit`, `x-unknown`, `unknown` label | decoded as UTF-8 if valid UTF-8, else with the fallback charset, else verbatim | `rfc2047.unknown_charset`, recovered or unsupported |

### ROB-030-004 — raw UTF-8 and 8-bit text, fallback charset: done

Applies to `Header.Text`, `DecodeHeaderText` and variants, not to parameter
values.

- Valid UTF-8 outside encoded words passes through; one `rfc2047.raw_utf8`
  (info) per value.
- Text that is not valid UTF-8, per run between encoded words:
  with `FallbackCharset` it is converted as a whole through `CharsetReader`
  (`header.invalid_utf8`, recovered); if the fallback cannot be applied each
  invalid byte becomes U+FFFD (`header.invalid_utf8`, unsupported, `Cause`
  set); with no fallback each invalid byte becomes U+FFFD
  (`header.invalid_utf8`, invalid_metadata). Valid UTF-8 is never converted.
- The fallback also decodes a word labelled `us-ascii` or `unknown-8bit` whose
  bytes are 8-bit and not valid UTF-8 (`charset.declaration_suspect` /
  `rfc2047.unknown_charset`). A word with a real label is never re-interpreted.
- A word declared `utf-8` (or converted by the hook) whose result is not valid
  UTF-8: each invalid byte becomes U+FFFD, `charset.invalid_sequence`.
- The result is always valid UTF-8. The raw bytes stay in `Header.Get`/`Raw`.

### ROB-030-005 — decoded CR/LF/NUL: done, neutralised

In text an encoded word decodes to: CR and LF become one space each, a CRLF
pair one space, **NUL becomes U+FFFD** (not removed, so two tokens are never
joined by the removal). Reported as `rfc2047.header_injection`, recovered. This
holds for header text and for parameter values, including a CRLF split across
two adjacent words.

CR, LF or NUL already present in the raw value outside encoded words are not
touched here; they are the header layer's (`header.bare_cr`, `header.nul`).

### ROB-030-006 — count, nesting-like work, expansion: done

- One forward pass. `=?` and `?=` are found by cursors that never move back; a
  candidate that is not a word costs at most its distance to the next
  candidate; a word's bytes are decoded once. `=?=?=?…`, `=?x?B?` repeated
  before a single `?=`, and thirteen more 1 MiB shapes run in milliseconds
  (`TestDecodeHeaderText_linear`).
- 10 000 words are decoded per value (`maxEncodedWords`), counting words left
  verbatim. The rest of the value is left as written:
  `rfc2047.word_limit`, limit_exceeded.
- Charset label at most 128 bytes.
- Output of a hook reader is capped at 6 × input + 1 KiB per run; past that the
  run is left verbatim.
- Under `Header.Text`, `DecodeHeaderText` and `Parse`, a hook reader is given up
  after 100 consecutive reads that return nothing and take nothing, and the
  hook is not asked again for that value.
- 64 diagnostics per value.

## Behaviour changes to existing API

- `Header.Text` / `HeaderFields.Text` / `mail.Header.Subject`: on an unknown
  charset the returned string is now the partial decoding rather than the raw
  value (identical when the value is that one word). Raw text that is not valid
  UTF-8 comes back with U+FFFD instead of the raw bytes. Decoded CR/LF/NUL are
  neutralised. A stalling hook reader no longer spins.
- Parameter values: a word that cannot be decoded no longer makes the whole
  value raw; the other words of the value are decoded. A stalled value is
  still returned whole and raw, with the one `header.decoder_no_progress`.
- `CharsetReader` receives the label without an RFC 2231 language suffix, and
  the joined bytes of a run of adjacent words. It is not called for
  `iso-8859-1`, `utf8`, `ascii` or the placeholder labels.

No existing test expectation had to change.

## Known limitations

- Raw ISO-2022-JP (7-bit, escape sequences) outside encoded words is valid
  ASCII and is not detected; the fallback only applies to text that is not
  valid UTF-8.
- A fallback is applied to a whole run of raw text. A value mixing UTF-8 and
  another 8-bit charset in one run is converted as the fallback charset.
- A word declared `utf-8` that holds another charset is not re-interpreted
  with the fallback: truncated UTF-8 would be destroyed by doing so.
- `iso-8859-1` is decoded as ISO 8859-1, not as windows-1252.
- Joining adjacent words assumes they are pieces of one byte stream. Words
  that each carry their own byte-order mark (UTF-16) keep the later marks as
  U+FEFF.
- `rfc2047.illegal_location` knows quoted strings only by counting unescaped
  `"`; it does not know the grammar of the field. Comments and other positions
  RFC 2047 forbids are not diagnosed.
- The legacy `Header.ContentType`/`ContentDisposition` path still waits for
  ever on a hook reader that returns `(0, nil)` for ever (pinned by
  `TestParse_metadataNoProgressIsOurs`); `Parse` and header text do not.
- `mail.ParseAddress`/`AddressList` still decode display names with the
  standard library decoder; they are outside this item.
- `mail.Header.Subject`'s comment still says the raw value is returned on
  error; `mail/` was not edited here.
